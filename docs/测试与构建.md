# CopyShare 测试与构建

> 文档导航：[用户指南](用户指南.md) · [故障排查](故障排查.md) · [开发指南](开发指南.md) · [架构与扩展点](架构与扩展点.md) · [局域网协议](局域网协议.md)

本文定义 CopyShare 的本地质量门禁、开发构建、安装包构建和发布前检查。命令默认从仓库根目录执行，注明 `src-tauri` 的命令除外。

## 1. 测试分层

| 层级 | 命令 | 覆盖范围 |
| --- | --- | --- |
| Node 行为与结构测试 | `node --test tests/*.test.ts` | 页面契约、Store、配置、文档、i18n、工作流和跨文件接线 |
| TypeScript 与前端构建 | `npm run build` | `vue-tsc --noEmit` 与 Vite production build |
| Rust 编译检查 | `cargo check` | Rust 类型、依赖和生产代码编译 |
| Rust 完整测试 | `cargo test` | 同步、传输、持久化、恢复、网络和平台逻辑 |
| 差异检查 | `git diff --check` | 空白错误和冲突标记 |
| 桌面运行验证 | `npm run tauri:dev` | Tauri command/event、托盘、剪贴板、窗口和系统集成 |

结构测试不是运行时端到端测试。涉及窗口、系统剪贴板、文件权限、网络或安装器时，还需要在对应平台执行桌面验证。

## 2. 快速定向验证

修改单个功能时，先运行相关测试文件：

```powershell
node --test tests/onboardingWizard.test.ts
node --test tests/architectureDocs.test.ts
```

Rust 可使用一个过滤条件：

```powershell
cd src-tauri
cargo test safe_json_store
cargo test file_transfer
```

定向测试只用于缩短反馈时间，不能替代提交或打包前的完整门禁。

## 3. 完整质量门禁

建议按以下顺序执行：

```powershell
node --test tests/*.test.ts
npm run build
cd src-tauri
cargo check
cargo test
cd ..
git diff --check
```

通过标准：

- 所有 Node 测试通过，没有失败或取消。
- `npm run build` 完成类型检查并生成 `dist/`。
- `cargo check` 无编译错误；新增警告需要解释或修复。
- `cargo test` 无失败；平台环境测试如被忽略，应记录名称和原因。
- `git diff --check` 返回 0；Windows 的 LF/CRLF 提示不等同于空白错误。

## 4. 开发与前端构建

### 桌面开发模式

```powershell
npm run tauri:dev
```

Tauri 会执行 `npm run dev`，前端开发服务器监听 `127.0.0.1:1421`，并启动 Rust 桌面进程。

### 纯前端开发

```powershell
npm run dev
```

纯浏览器模式适合布局和响应式检查，但没有 Tauri bridge。桌面命令报 `window.__TAURI_INTERNALS__` 缺失时，不应据此判断生产桌面构建失败。

### 前端生产构建

```powershell
npm run build
```

该脚本先执行 `vue-tsc --noEmit`，再运行 Vite production build，输出到 `dist/`。

## 5. 本地主程序与安装包

### 只构建主程序

```powershell
npm run build:exe
```

该命令执行 `tauri build --no-bundle`，Windows 主程序通常位于：

```text
src-tauri/target/release/CopyShare.exe
```

### 构建当前平台安装包

```powershell
npm run tauri:build
```

该命令会再次运行前端生产构建，再编译 Rust release 并根据 `tauri.conf.json` 的 `bundle.targets = "all"` 生成当前平台支持的 bundle。

Windows 常见产物：

```text
src-tauri/target/release/bundle/nsis/CopyShare_<版本>_x64-setup.exe
src-tauri/target/release/bundle/msi/CopyShare_<版本>_x64_en-US.msi
```

产物名称会随版本、架构和打包器变化，不要在脚本中依赖示例文件名；应枚举对应 bundle 目录并核对大小、修改时间和 SHA-256。

## 6. 安装包核验

Windows 可使用 PowerShell 记录哈希：

```powershell
Get-ChildItem src-tauri/target/release/bundle -Recurse -File |
  Where-Object { $_.Extension -in '.exe', '.msi' } |
  ForEach-Object {
    [pscustomobject]@{
      Path = $_.FullName
      Bytes = $_.Length
      SHA256 = (Get-FileHash -Algorithm SHA256 $_.FullName).Hash
    }
  }
```

至少验证：

- 文件存在且大小不是 0。
- 文件修改时间属于本次构建。
- SHA-256 已记录，可与发布资产核对。
- 在干净测试环境安装、启动、退出和卸载正常。
- 首次向导、设备连接、系统权限和升级路径在安装版中可用。

## 7. GitHub Release 构建

`.github/workflows/release.yml` 在推送 `v*` 标签或手动触发时构建：

- Windows x64 NSIS
- Windows ARM64 NSIS
- macOS Apple Silicon
- macOS Intel
- Linux

工作流使用 Node.js LTS、Rust stable 和 `tauri-apps/tauri-action`，上传工作流产物并创建 GitHub Release 草稿。草稿在资产、大小、哈希和平台结果全部核对前不应公开。

### 更新签名配置

`tauri.conf.json` 已启用 `createUpdaterArtifacts`，应用只接受对应公钥签名的更新。当前本机的私钥位于 `C:\Users\SuZe\.tauri\copyshare-updater.key`，公钥旁存为 `.key.pub`；私钥在仓库外，必须另行安全备份。不要重新生成密钥覆盖已发布应用的公钥，否则老版本无法验证新更新。

发布前将私钥文件内容配置为 `suzeccc/CopyShare` 的 GitHub Actions Secret `TAURI_SIGNING_PRIVATE_KEY`。下面的命令通过标准输入上传，不将私钥打印到终端：

```powershell
Get-Content -LiteralPath "$env:USERPROFILE\.tauri\copyshare-updater.key" -Raw |
  gh secret set TAURI_SIGNING_PRIVATE_KEY --repo suzeccc/CopyShare
```

当前密钥无口令；若以后使用有口令的密钥，还需设置 `TAURI_SIGNING_PRIVATE_KEY_PASSWORD`。本地构建签名 NSIS 安装包：

```powershell
$env:TAURI_SIGNING_PRIVATE_KEY = "$env:USERPROFILE\.tauri\copyshare-updater.key"
$env:TAURI_SIGNING_PRIVATE_KEY_PASSWORD = ""
npm run tauri:build -- --bundles nsis
Remove-Item Env:TAURI_SIGNING_PRIVATE_KEY
Remove-Item Env:TAURI_SIGNING_PRIVATE_KEY_PASSWORD
```

工作流会上传签名安装包、`.sig` 和 `latest.json`，Windows 更新优先使用 NSIS。更新源是 `https://github.com/suzeccc/CopyShare/releases/latest/download/latest.json`；Release 必须公开且清单中的版本号大于已安装版本，客户端才会发现更新。草稿、仅上传便携 EXE 或缺少签名清单均无法提供应用内更新。

正式启用前在测试环境安装一个支持更新的较旧安装版，再发布更高版本，验证下载、签名、安装、配置保留和重启。旧版应用需手动安装一次支持更新的安装包；浏览器 IPC 模拟检查不能代替真实安装升级验证。

本地打包不等于正式发布：不要因为 `npm run tauri:build` 成功就自动修改版本、创建标签、推送或公开 Release。

- [ ] 完整 Node、前端和 Rust 门禁通过。
- [ ] 新配置字段有默认值、迁移和老用户测试。
- [ ] 协议变化有能力协商、兼容说明和序列化测试。

## 9. 常见构建问题

### `vue-tsc` 失败

先处理报错文件中的类型不一致；不要使用跳过类型检查的构建命令掩盖问题。重点检查 Rust camelCase 序列化字段与 TypeScript 类型是否同步。

### Cargo 编译或测试失败

使用第一条真实编译错误定位根因。模块拆分后测试若访问私有实现，优先改为行为测试或 `cfg(test)` 辅助接口，不要扩大生产 API。

### Windows 安装器工具失败

确认 Tauri 系统依赖、WiX/NSIS 工具链和目标架构就绪；保留完整 `tauri build` 输出，区分 release 编译失败与 bundle 阶段失败。

### 全仓格式检查产生大量既有差异

不要在脏工作树直接运行会重写全仓的格式化命令。先明确本次修改范围，对新增文件执行定向格式化，再使用编译、测试与 `git diff --check` 验证。
